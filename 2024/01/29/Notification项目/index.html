Project feature

Send notifications from alerts and subscriptions to recipients by email, webhook, and mobile app.

The Notifications screen (Administration → Notifications) allows you to configure alerts and subscriptions to send notifications to the appropriate recipients using email, webhook, and the Trend Vision One mobile app.

1. Business logic

notification center作为一个通知中心，他会把公司各个需要对外通知的service集成到一起，会根据各个service自己的业务特点提供不同配置，比如一些过滤条件，开关，发送频率，收件人等信息，用户可以针对各个service配置的不同场景来获取他们想要接收到的消息内容，然后notification会提供三种发信渠道，分别是email、webhook和mobile将各个service的alert发送给客户。其中后端这边维护了各个service所依赖的消息模版，支持html和markdown格式，并且消息支持L10N国际化。每日发送量达到百万封，qps可以达到500，除此之外，还会在一个小铃铛消息实时推送业务，实现公司内部各个service向客户端推送消息，比如项目新功能上线，模块迁移等通知

这个微服务主要集成了公司内部各个service alert,目的是实现公司产品与用户之间的信息交互。每个service可以根据自己的业务特点配置在notification这边，支持通过email，we bhook,mobile向用户发送通知 ，客户可以通过ui来对各个service event进行配置。根据不同的service选择不同过滤条件，当各个service特定事件发生时，收件人或收件人组进行接受通知。后端还维护着每个service特定的消息模版，支持json,html,markdown等多种格式，且支持L10n 国际化。公司每个月的openapi的changelog也是从这里发出，还有就是实现了console上对用户进行实时推送的小铃铛，从后端向ui推送一些公司内部各个service的一些需要告知客户的实时消息。从技术的角度来说，采用redis实现了缓存存储token合热点数据，通过redis的计数器功能实现了发送量的限制，通过分布式锁保证线程执行的可靠性，以及通过pub/sub和websocket实现刚才说的小铃铛实时推送的功能。使用mysql作为数据库，使用rabbitmq作为消息队列分发三种不同渠道的消息，当请求进入队列时，api立即回应，消息的处理与发送在队列里排队操作，这样大大加快了在高并发大数据量请求下api的响应的速度。后端还有一些自动化定时任务和消息埋点技术。去检测用户行为以便作为更好的优化。

集成了若干service alerts和subscription,可以对期望的service，email,webhook,mobile进行配置，ui上还有小铃铛，小铃铛的数据是记录在nc-v2 mongodb中,后端定义数据ttl是7天，7天后所有到期的数据会自动清理掉，前端只能看，不能操作，每次给客户展示的是7天前至今的数据。

schedule job：定期检查用户在各个event上的配置情况，接lifecycle实时purge无效company。是用了redis分布式锁，进行加锁，让定时任务在多台服务器的情况下只会执行一次，set nx ex

2. Email Deliver Status Tracking

We track email deliver status using ses monitoring ability.

2.1 Design

The flow is shown in the follow picture，and contains these steps:

  1. nc-v2 calls SES api to send email and specifying a configurationSet and set event destination to SNS
  2. ses delivers the email to customer’s email server
  3. email server return deliver status of the email to SES
  4. SES convey the deliver status to a SNS topic
  5. SNS triggers a lambda function and writes the deliver status to nc-v2 DB

2.1.1 Create a ses configuration set

3. Email User Behaviour Tracking

We track behaviour when user opens an email or clicks a link in email.

AWS会去埋点 用的是AWS自己的URL，可能会被用户的firewall拦截，所以最后就没用aws ses 自带的

3.1 Design

To track user opening an email, we plant a 1 pixel picture from download center at the end of the email content. When user opens the email, the picture is automately downloaded and a new access log will be created in download center’s access log bucket. And we use a lambda to monitor the created access log and convert it to a UBT log and send it to slog.

To track user clicking a link in email, we add additional query parameters at the end of each url link in the email. When user clicks the link and goes to uic portal pendo will record the url, thus we can have statistics on how many user click the links in email.

5. Mobile

在调用通用接口createNotification发信时，对于mobile channel，先把各个app 发送的alert 数据by account的写进mongodb中，由于这是第一次进来的数据，肯定是未读的，所以记录一个字段unread :true,带进mongodb，ttl两周，记录unread数，存入redis,再用户后面一条一条读或成批读的时候，会根据更新unread 为false, 用户在list mobile notification的时候，这个时候要显示未读数量，后端首先会获得当前account的record，根据unread的状态判断该条notification用户是否已读。以此来记录unread数量，并存入redis中保存。这个时候，各个app的alert信息还在往这个account 的mobile里送，新送的消息还是未读的，但是需要先拉一把redis里存的之前的用户未读数（因为用户可能有读过的了），sync一下总的unread数在再存入redis中。

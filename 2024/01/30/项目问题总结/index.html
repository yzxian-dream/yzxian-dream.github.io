项目问题总结

Ring bell & Websocket

1 Ring bell notifications

ring bell notifications are to send real time notifications to users that are currently login to V1 console.

当每个服务器记录连接，保存在内存ConcurrentHashMap当中
当需要推送websocket消息的时候，同时在redis发布一个消息
每个服务器订阅redis的消息，当监听到有消息时，每台服务器遍历自己内存当中的连接进行发送
这样我们就可以实现websocket的分布式部署，当然redis订阅和发布也可以用其他消息队列工具类实现
————————————————

1.1 Desgin

The design is simple:

  • store ring bell notification in mongoDB when it creates, and the ttl of each notification is 14 days.

  • get all notification from DB that is meant to be seen by the current login account via RBAC

  • Websocket is used to send ring bell message to a login account.

Websocket向前端发送消息的两种方式，一种是发向小🔔，两种type ,但实际通过websocket发送的是未读数，只有当点小铃铛的时候前端才会调用一个接口去load这段时间的保存在mongodb中的未读的content内容和上次load的时间。这支api会load这个companyId下的所有消息（7天内的，ttl是7天）。

  • 0 - Informative (To be displayed under Bell’s “Informative” page)
  • 1 - Tasks (To be displayed under Bell’s “Tasks” page)

另一种是common type，就是直接通过webscket REDIS pubsub发向ui

2 Websocket 优化

websocket is used to ensure the real-time delivery of ring bell notifications. Websocket connection is established by a http request from user’s browser to nc-v2 when login.

When a ring bell notification is created, nc-v2 send a websocket message to browser and notify the user of there being a unread message in bell.

2.1 Desgin

Architecture:

data structure in each pod:

当用户在第一次登录的时候会call unread count api,我们会把webscoket url返回给前端，前端再去建立websocket连接。WebSocket是真正的全双工方式，建立连接后客户端与服务器端是完全平等的，可以互相主动请求。而HTTP长连接基于HTTP，是传统的客户端对服务器发起请求的模式。

当客户端与服务端建立websocket连接后，会以当前cid为基础订阅一个channel(比如channelName为websocketChannel+cid), 并获取当前cid和其account信息填充到项目初始化时在内存中创建的用于保存每个account的webscoket信息的concurrenthashmap中。是当前登录的account会订阅redis channel，并开启线程consumeOne持续监测消费channel里的内容，对外提供一只发送小铃铛的api，当有消息publish到channel后，就会触发对应的task先获取先前存入concurrenthashmap中的当前cid下的所有online account,找到这个account对应的websocket连接，通过这个链接WriteMessage到前端，前端监控到onmessage事件进行处理，或者循环account进行广播发送

加入redis pub/sub 的作用，使用这种机制，让所有节点的服务端都订阅同一个信道，然后当任意节点收到请求或消息后都可以触发发布机制，这样不管需要通知的用户在哪个节点上都可以收到消息，即使在不同的服务器中，两个用户之间也能互相收到消息，这样就完美的实现了多节点下的websocket通信，实现群发。

1.原先的逻辑：项目启动的时候会让各个pod 订阅一个redis channel,用户在登录的时候默认就会建立websocket连接，这个连接是随机的建在notification的pod上的，所以要向某个user发送小铃铛消息的话，它需要进行一个广播，所以这边就采用了一个redis的pub/sub机制，首先一个请求打过来，打到notification的其中一个pod上，pod会把这个message publish到channel中，所有订阅这个channel的pod都会拿到这个信息，然后再去找对应的user,找到了之后才会去发，因为一个user只会连在一个pod上，所以可以保证一个user只会发一次。

这个API返回铃声通知的未读计数和建立websocket连接的url。

调用API后，UI将尝试与nc-v2建立一个新的websocket连接。当选项卡关闭或刷新时，websocket连接将断开。

避免WebSocket推送太多的方法可以包括：

  1. 使用redis消息队列来限制推送频率，确保不会发送过多的消息。
  2. 在客户端和服务器端都设置合理的心跳间隔，避免频繁的连接和断开操作。
  3. 对于不必要的数据，可以进行压缩或者合并处理，减少推送的数据量。
  4. 使用流量控制算法，根据当前系统的负载情况动态调整推送频率。

3 Websocket Enhancement

2.1 Background

Currently, nc-v2 uses only one redis pub/sub channel to publish and subscribe websocket messages of all connections. However, Pub/Sub clients have a default hard limit of 32 megabytes and a soft limit of 8 megabytes per 60 seconds. There is a high chance nc-v2 would exceed this limit if websockets are used more frequently in the future.

2.2 Design

Divide the pub/sub channel to customer level, the websocket connections which belong to the same customer shares one pub/sub channel.

And every time a send websocket message request is triggered, nc-v2 only publish message to one channel according to the targeted customer of the request.

RabbitMq的消息堆积

线上出现过消息堆积导致的cpu使用率飙升的情况

RabbitMQ 是一种消息中间件，用于在应用程序之间传递消息。当消息堆积过多时，可能会导致 CPU 飙升的原因有以下几点：

  1. 消息过多导致消息队列堆积：当消息的产生速度大于消费者的处理速度时，消息会积累在消息队列中。如果消息堆积过多，RabbitMQ 需要不断地进行消息的存储、检索和传递操作，这会导致 CPU 使用率升高。

  2. 消费者无法及时处理消息：消费者处理消息的速度不足以追赶消息的产生速度，导致消息不断积累在队列中。这可能是由于消费者出现瓶颈，无法处理足够多的消息，或者消费者的处理逻辑复杂，导致消费过程耗费过多的 CPU 资源。

  3. 消息重试导致额外的 CPU 开销：当消息处理失败时，消费者可能会进行消息的重试操作，尝试再次处理消息。如果重试频率较高，会导致消息在队列中频繁流转、被重复消费，这会增加额外的 CPU 开销。

  4. 过多的连接以及网络IO：当消息堆积过多时，可能会引发大量的连接请求和网络数据传输。这会增加网络 IO 的负载，并占用 CPU 资源。

预防措施

生产者

减少发布频率,考虑使用队列最大长度限制

消费者

增加消费者的处理能力 //优化代码；使用JDK的队列缓存数据，多线程去处理（若考虑顺序问题，就采用单例线程）
默认情况下，rabbitmq消费者为单线程串行消费（org.springframework.amqp.rabbit.listener.SimpleMessageListenerContainer类的concurrentConsumers与txSize（对应prefetchCount）都是1），设置并发消费两个关键属性concurrentConsumers和prefetchCount。concurrentConsumers：设置的是对每个listener在初始化的时候设置的并发消费者的个数；prefetchCount：每次从broker里面取的待消费的消息的个数。

配置方法：修改application.properties：
spring.rabbitmq.listener.concurrency=m
spring.rabbitmq.listener.prefetch=n

prefetchCount(prefetch)
The number of messages to accept from the broker in one socket frame. The higher this is the faster the messages can be delivered, but the higher the risk of non-sequential processing. Ignored if the acknowledgeMode
is NONE. This will be increased, if necessary, to match the txSize

concurrentConsumers(concurrency)
The number of concurrent consumers to initially start for each listener.

concurrentConsumers默认值为1，prefechCount默认值为250，可以通过调整这两个参数来加速consumer端的消费。

concurrentConsumers是设置并发消费者的个数,可以进行初始化-最大值动态调整,并发消费者可以提高消息的消费能力,防止消息的堆积
prefechCount是每个消费者一次性从broker中取出的消息个数,提高这个参数并不能对消息实现并发消费,仅仅是减少了网络传输的时间

RabbitMq消息发送可靠发送

rabbitmq的自动ack机制的问题

  • 潜在的消息丢失：如果消费者在处理消息时发生错误或崩溃，而且没有手动ack确认消息，那么消息可能会丢失。
  • 消费者无法控制消息处理速度：自动ack机制会导致消费者无法控制消息的处理速度，可能会导致消息堆积或者处理过慢。
  • 难以进行消息重传：由于消息在自动ack模式下会立即被确认，消费者无法进行消息的重传，导致消息丢失或重复处理的问题

解决方法：开启手动ack机制和重试机制

首先开启rabbitmq持久化机制

确保消息成功发送：一方面需要确认publish—>exchange—->queue的ack,当确保进消息进queue后，api立即响应response,后面的流程由消费端继续进行逻辑处理，这样来解决线上高并发大数据量的请求而导致的api延迟的问题。

确保消息成功被消费：另一方面要开启消费端手动ack的confirm机制 queue—>consumer来保证消息的可靠性发送，并建立retry机制以及死信队列来将发送失败的邮件信息持久化后延迟发送。

Publisher Acknowledgements机制

开启confirms回调 P -> Exchange是配置消息到达交换器的确认回调，第二行则是配置消息到达队列的回调。

spring.rabbitmq.publisher-confirm-type=correlated （属性的配置有三个取值）

  1. none：表示禁用发布确认模式，默认即此。
  2. correlated：表示成功发布消息到交换器后会触发的回调方法。
  3. simple：类似 correlated，并且支持 waitForConfirms() 和 waitForConfirmsOrDie() 方法的调用。

开启returnedMessage回调 Exchange -> Queue

spring.rabbitmq.publisher-returns=true

接下来要开启两个监听，具体配置如下：

  1. 声明了一个业务队列、一个业务交换机、一个死信队列、一个死信交换机。其中声明业务队列时的 x-dead-letter-exchange 参数指定队列的死信交换机，当信息被判定为死信时就会被Broker自动转发给配置的死信交换机.
  2. 定义配置类，实现 RabbitTemplate.ConfirmCallback 和 RabbitTemplate.ReturnsCallback 两个接口，这两个接口，前者的回调用来确定消息到达交换器，后者则会在消息路由到队列失败时被调用。
  3. 定义 initRabbitTemplate 方法并添加 @PostConstruct 注解，在该方法中为 rabbitTemplate 分别配置这两个 Callback。

生产消息

consumer Acknowledgeement机制

在消费者端设置重试次数

channel.basicAck(deliveryTag, multiple);

consumer处理成功后，通知broker删除队列中的消息，如果设置multiple=true，表示支持批量确认机制以减少网络流量。

channel.basicNack(deliveryTag, multiple, requeue);

consumer处理失败后，例如：有值为5,6,7,8 deliveryTag的投递。

如果channel.basicNack(8, true, true);表示deliveryTag=8之前未确认的消息都处理失败且将这些消息重新放回队列中。

  • deliveryTag：long - 消息投递的唯一标识，作用域为当前channel

  • multiple：boolean - 是否启用批量确认机制

  • requeue：boolean - 消息处理失败是重新放回队列还是直接丢弃

ResendMsg定时任务重新投递发送失败的消息

说明: 每一条消息都和exchange routingKey绑定, 所有消息重投共用这一个定时任务即可

redis过期时间失效

为了避免ses throttling error导致的发信失败，在代码内部针对各个service的发信分别做了限制，是通过redis利用incr和expire来限流，但是在高并发情况下导致过期时间失效问题.

由于redis incr操作，当key不存在时，会生成这个key并将其值初始化为0，并且默认设置key的有效时间为24小时.

首先创建了一个RedisService类，该类使用Spring的StringRedisTemplate来与Redis进行交互。然后，我们定义了一个atomicOperation方法，该方法使用StringRedisTemplate的execute方法来执行一个事务。在这个事务中，我们执行了一次增加操作和一次设置过期时间操作。由于这些操作是在事务中执行的，所以它们是原子性的，即要么全部成功，要么全部失败。

需要注意的是，虽然Redis的事务可以保证操作的原子性，但是它并不支持回滚，也就是说，如果事务中的某个操作失败，那么该操作之前的所有操作仍然会被执行，而该操作之后的所有操作都会被取消。

mysql字段类型的数据范围超出

对于recipient字段设定的数据类型是varchar(1000),但是当用户在ui上增加的收件人越来越多时，可能会超出上限导致保存失败，字符串会被切断。所以将该字段类型改为varchar(3000)或者text来解决数据大小限制

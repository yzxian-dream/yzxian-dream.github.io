Overall Framework

Glossary

  • UIC: UI container, consists of the frontend and the backend. The frontend provides the container surrounding the app. While the backend exposes many APIs for the app to use. Also, UIC manages the XDR users and their devices.
  • SVP: Service Platform, sits in front of the app server. All the interactions with the app from outside, e.g. UIC, other apps, external API calls, must go through the SVP to touch the app server.

Service Platform是VisionOne的服务级中间件，它提供统一的入口点、认证方法和API节流，帮助对跨站点或跨云API调用的API和隧道服务进行认证和转换。

service platform 它是我们公司平台的服务级中间件，作为一个api gateway提供了统一的入口点，来代理请求到各个微服务,并为其制定了一些规则。首先请求会根据路径的router predicate进行路由断言，当路由匹配之后就会进入实现制定的一些fileter过滤器，比如我们会对所有的请求进行一个global filter的jwt token鉴权，也会对一些请求附加额外的公共的header用来指示客户或RBAC信息，将请求转发到应用服务器。

首先每个app必须在nacos注册中心中将自己的服务名和ip地址注册自己的服务，网关会更根据请求来判断它应该由哪个微服务来处理，这个判断的过程就是网关的路由，sp知道被访问的服务后就会去注册中心拉取这个服务的列表，然后通过负载均衡挑取一个实例，将请求发送到对应的应用实例，这个过程就是网关的转发

对应上一个productcode也就是产品编号，sp会制定对应的url 前缀，比如internal/v2/direct/dlt, 其他app 如果想要访问当前app的话，就需要访问sp的fqdn + url前缀 +对应app的api url，并且还需要在请求头中带上authorazation jwttoken。对于大部分的业务sp在校验token成功之后就会转到对应的下游服务获取数据在返回给请求的app。对于某些特定的请求，sp还会额外加一下请求头。如果请求是从console上来的，在用户成功登录访问某个app时，uic在拿到前端资源渲染完iframe后会将请求代理到sp，sp后续继续进行代理，sp根据产品代码检索对应app的fqdn，然后帮忙加上对应的认证头，会附加一些公共的header用来指示客户或RBAC信息，将请求转发到应用服务器。

各个app首先要申请一个密钥对，公钥由自己保存，私钥交由sp保存，第一次会给到各个app一个servicetoken, 并且会提供一个callbackurl进行定期renew这个serviceToken, 它的作用是可以在各个微服务中将其作为header auzaration去生成customerToken，各个app，customerToken才是gateway和各个微服务中真正对请求的鉴权。

Service Platforn (SVP) sits in front of the app server. All the interactions between V1 Apps or from outside to V1 Apps/Services, e.g. UIC, other apps, external API calls, must go through the SVP to touch the app server.

Inbound is a submodule which is responsible to process request, and dispatch to Outbound.

  • in-bound: For in-bound API calls to Service Platform, Service Platform requires per tenant API key for authentication.
  • out-bound: For out-bound API calls from Service Platform, Service Platform can conform to API consumers’ trust models (trust all, per tenant API key or per role API key).

外部的api请求打到app service,需要一下请求url format。 SVP_FQDN/internal/v1/direct/appX/Path

  • Common Resources for App The JWT token for app to authenticate itself to the SVP to request APIs The JWT pem file for the app to verify the requests from the SVP, the JWT token and pem are provided offline.

Request & Response Procedure

  1. The user login the portal. If the user login for the first time, UIC will create a record for the customer.

  2. The user clicks the icon in the left bar to navigate to the app, the browser will navigate to V1_FQDN/#/app/appX_route (this is defined by UIC)

  3. UIC will render the iframe with the source provided by the app.
    The path provided by an app request will finally also be the path that app gets requested.
    For example, the ANI app sets the “/ui/ani/fes/index.html“ as its src for iframe, then the ANI app server will finally get the request for “https://nsi-int.visionone.trendmicro.com/**ui/ani/fes/index.html**”:

    UIC provides the proxy for 3 kinds of Paths:

    1. /ui/appX/…, usually used for frontend resources request
    2. /static/appX/…, this indicates the UIC to cache the resouce on UIC server
    3. /public/appX/.., used for public API request (include open API & console)

  4. UIC will then proxy the request to SVP, rewriting the request url to be SVP_FQDN/internal/v2/direct/appX/Path

  5. External API requests to the app also follows SVP_FQDN/internal/v2/direct/appX/Path

  6. App can choose to listen for the customer/device lifecycle events, i.e., the CRUD of the customer/device (UIC Customer / Device Lifecycle APIs). UIC will send a request to the app registered URL through SVP, also following SVP_FQDN/[internal|service]/v2/direct/appX/Path (Route path guideline)

  7. SVP will continue to proxy the reqeust:

    1. Retrive the app FQDN based on the product code appX
    2. Generate the authentication header (usually JWT token signed by SVP) for the app
    3. Attach some additional headers (SP Common Headers) to indicate the customer or RBAC infomation
    4. Forward the request to the app server APP_FQDN/Path

  8. If the app wants to requst the APIs of UIC or other apps, it must also go through the SVP (Service Platform Routing). For example, if the app needs to reqeust an API of UIC, it should make a request to the SVP with the URL being SVP_FQDN/[internal|service]/v2/direct/uic/Path (uic is the product code of UIC). Also, app needs to authenticate itself to the SVP.

To access resources, requests must contain an authorization header with an authentication token. The following is an example of a request with a valid authorization header.

  • App’s API should get customerID from SP request JWT payload (same as header “x-customer-id”), instead of used customerId in query path or body.
    • Unless just want to get some customer’s configure data, such as customer’s region.
  • Service Token (customerId is 00000000-0000-0000-0000-000000000000) is used for service to service API, such as got onboarded customers list from UIC API, generate customer token.
  • Customer Token is used for the request related to specified customer, such as get connected product of a customer from UIC API.
  • Device Token is used for Device/Applicance/Agent/App side of App, generally they should only have API permission of same App’s external API.
    • This is not implemented yet, if needed may can discusss with us for detail user case

  2. App->SVP, only under GIS transit gateway or add App’s outbound IP to SP’s ACL will be able to access V1’s internal API, otherwise can only access public or external APIs.

Purpose

For security reason, Service Platform will only open necessary APIs to Internet, so we need App’s API explicitly tell us what’s their API purpose by prefix, that’s why we need App team to follow this guideline. This guideline defines SP rewrite API path rules

API prefix Guideline for Apps

For V1 App/service APIs, we can category them as the following:

  1. /ui/appX/…, used for Console frontend resources request
  2. /static/appX/…, used for Console frontend static resource (js, json, css and etc), this indicates the UIC to cache the resouce (Suggest to add versioning or hashing to file path to avoid conflict between different versions.)
  3. /public/appX/.., used for public API (released in Automation Center), or candidate for public API, also may be used for Console frontend.
  4. /internal/appX/…, used for internal service request (should not used in Console frontend)
  5. /external/appX/…, used for external API request (still V1 service, but from Internet, maybe Appliance/ Agent in on-prem environment, or Point Product)
  6. /service/appX/…, used for service to service API, SP will only allow Service Token to call it
  7. /…, others don’s use the above prefix, default will only be accessable in Internal Ingress.

Springcloud Gateway

有了网关之后，后端各个微服务的IP地址就不需要暴露给前端了，要暴露的仅仅是网关地址，具体的前端请求会直接到达网关，对于前端来说后端就是个黑盒，网关通过负载均衡来找到具体的微服务实例获取数据返回。对于前端分布式部署的微服务后端和单体架构没什么区别.api gateway提供了简单而有效的统一的api路由管理方式，基于路由断言来做路由规则，并且基于Filter链的方式提供了网关的基本功能，例如鉴权，安全，限流，日志监控。

springcloud gateway是基于webflux框架的，使用Reactor模式，而webflux框架底层使用的netty,这是基于异步非阻塞IO进行开发的

自定义filter要保证在nettyRoutingFilter之前执行，nettyRoutingFilter的order值是int max_value，也就是优先级最低，最后执行，用来做请求转发的,自定义的order小于它就行,其中exchange是请求上下文，执行完当前过滤器后就要通过过滤器链chain继续向后执行

网关—>微服务

网关设置自定义过滤器做拦截，来校验jwttoken,校验成功获取用户信息存入，通过exchange.mutate的api来修改请求，添加请求头添加用户信息，这样网关在发请求到微服务的时候就会在header里带上用户信息，微服务通过添加一个类A来实现springmvc拦截器（HandlerInterceptor）来进行请求解析，获取用户信息存入threadLocal中，后续所有的业务都可以从threadLocal中取出用户信息执行业务。添加一个配置类实现WebMvcConfigurer来将类A注册进去。

这个配置类需要配spring扫描到才能生效

rabbitmq

消息指的是两个应用间传递的数据。数据的类型有很多种形式，可能只包含文本字符串，也可能包含嵌入对象。

“消息队列(Message Queue)”是在消息的传输过程中保存消息的容器，本质上是一个队列，FIFO先进先出。在消息队列中，通常有生产者和消费者两个角色。生产者只负责发送数据到消息队列，谁从消息队列中取出数据处理，他不管。消费者只负责从消息队列中取出数据处理，他不管这是谁发送的数据。

常见的比如rabbitmq, rocketmq, kafka，nodejs里的bull, go的asynq,都是比较好用的消息队列。

rabbitmq介绍

RabbitMQ是由erlang语言开发，基于AMQP（Advanced Message Queue 高级消息队列协议）协议实现的消息队列。

所谓协议就是双方之间达成的约定和规矩，双方必须都按照这个约定来执行操作，否则会导致一方看不懂另一方的行为而无法做出响应。一个协议定义了在两个或多个通信实体之间交换的报文格式和次序，以及报文发送（或接收报文或其他事件）所采取的行动。

消息队列本质上是一个外部的多线程的机制，项目内部使用线程池来做是可以降低响应时间，实现并行，但是项目内部使用太多线程并行还会出现耦合和大量消耗cpu的情况，把这个交由消息队列（中间件rabbitmq）来做，节约内存空间，削峰。消息队列的话如果以后还需要加什么业务，不需要停止项目加code，而是通过消息队列外扩，比如加个微信服务之类的。

rabbitmq组成部分

Broker ：即RabbitMQ的实体服务器。提供一种传输服务，维护一条从生产者到消费者的传输线路，保证消息数据能按照指定的方式传输。此进程包括两个部分：Exchange和Queue。
Exchange ：消息交换机。指定消息按照什么规则路由到哪个队列Queue。
Queue ：消息队列。消息的载体，每条消息都会被投送到一个或多个队列中。
Binding ：绑定。作用就是将Exchange和Queue按照某种路由规则绑定起来。
Routing Key：路由关键字。Exchange根据Routing Key进行消息投递。定义绑定时指定的关键字称为Binding Key。
Vhost：虚拟主机。一个Broker可以有多个虚拟主机，用作不同用户的权限分离。一个虚拟主机持有一组Exchange、Queue和Binding。
Producer：消息生产者。主要将消息投递到对应的Exchange上面。一般是独立的程序。
Consumer：消息消费者。消息的接收者，一般是独立的程序。
Connection：Producer 和Consumer 与Broker之间的TCP长连接。
Channel：消息通道，也称信道。在客户端的每个连接里可以建立多个Channel，每个Channel代表一个会话任务。在RabbitMQ Java Client API中，channel上定义了大量的编程接口。

首先要理清一下在整个信息传输流程中各个组件的租用

1. connection:

首先要把producer和connection与rabbitmq broker之间建立连接，就是这里的connection,是Producer／Consumer和Broker之间的TCP连接。断开连接的操作只会在Producer/Consumer端进行，Broker不会断开连接，除非出现网络故障或者Broker服务出现问题，Broker服务宕了。

2. channel:

区别于rabbitmq broker内部的建立的q, channel是建立在真实的TCP connection连接内的虚拟连接（是我们与RabbitMQ打交道的最重要的一个接口）。仅仅创建了客户端到Broker之间的连接后，客户端还是不能发送消息的,需要为每一个Connection创建Channel，AMQP协议规定只有通过Channel才能执行AMQP的命令。在代码中并不会有直观的能看到信道这个概念。因为代码中会通过springboot框架自动配置。

AMQP的命令都是通过信道发送出去的（我们大部分的业务操作是在Channel这个接口中完成的，包括定义Queue、定义Exchange、绑定Queue与Exchange、发布消息等）也就是rabbitmq在一个TCP上面建立成百上千的信道来达到多个线程处理。

注意是一个TCP 被多个线程共享，每个线程对应一个信道，信道在rabbit都有唯一的ID，保证了信道的私有性，对应上唯一的线程使用。如下图所示，

  • 为什么RabbitMQ 需要信道，如果直接进行TCP通信呢？

    上述的描述其实已经很明显了，因为TCP可以被多个线程共享，显然线程比TCP要省事的多。TCP的创建开销很大，创建需要三次握手，销毁需要四次握手。如果不使用信道，那么引用程序就会使用TCP方式进行连接到RabbitMQ，因为MQ可能每秒会进行成千上万的链接，总之就是TCP消耗资源，TCP链接可以容纳无限的信道，不会有并发上面的性能瓶颈。

3. exchange:

交换机，rabbitmq的消息都是先到exchang上，不过exchange没有储存信息的功能，会找到与其绑定的queue，当消息发送给queue（这里有常用的三种类型的交换机，direct，fanout，topic，每种类型都有对应的发送规则

直接翻译的话叫做主题交换机，如果从用法上面翻译可能叫通配符交换机会更加贴切。这种交换机是使用通配符去匹配，路由到对应的队列。通配符有两种：”*” 、 “#”。需要注意的是通配符前面必须要加上”.”符号。

* 符号：有且只匹配一个词。比如 a.*可以匹配到”a.b”、”a.c”，但是匹配不了”a.b.c”。

# 符号：匹配一个或多个词。比如”rabbit.#”既可以匹配到”rabbit.a.b”、”rabbit.a”，也可以匹配到”rabbit.a.b.c”。

rabbitmq的作用

  • 解耦：系统A在代码中直接调用系统B和C的代码，如果将来D系统接入，系统A还需要修改代码，过于麻烦

    如图所示。假设有系统B、C、D都需要系统A的数据，于是系统A调用三个方法发送数据到B、C、D。这时，系统D不需要了，那就需要在系统A把相关的代码删掉。假设这时有个新的系统E需要数据，这时系统A又要增加调用系统E的代码。为了降低这种强耦合，就可以使用MQ，系统A只需要把数据发送到MQ，其他系统如果需要数据，则从MQ中获取即可

  • 异步，将消息写入消息队列，非必要的业务逻辑（比如notification里的发送业务，message组装完成先进队列，进q即响应，后续的逻辑比如调用ses api发送email有消费端去q中取数据实现），加快响应速度

    如图所示。一个客户端请求发送进来，系统A会调用系统B、C、D三个系统，同步请求的话，响应时间就是系统A、B、C、D的总和，也就是800ms。如果使用MQ，系统A发送数据到MQ，然后就可以返回响应给客户端，不需要再等待系统B、C、D的响应，可以大大地提高性能。对于一些非必要的业务，比如发送短信，发送邮件等等，就可以采用MQ。

  • 削峰：并发量大的时候，所有的请求直接堆到数据库，造成数据库连接异常

    如图所示。这其实是MQ一个很重要的应用。假设系统A在某一段时间请求数暴增，有5000个请求发送过来，系统A这时就会发送5000条SQL进入MySQL进行执行，MySQL对于如此庞大的请求当然处理不过来，MySQL就会崩溃，导致系统瘫痪。如果使用MQ，系统A不再是直接发送SQL到数据库，而是把数据发送到MQ，MQ短时间积压数据是可以接受的，然后由消费者每次拉取2000条进行处理，防止在请求峰值时期大量的请求直接发送到MySQL导致系统崩溃。

可靠消息

对于rabbitmq，生产者定义交换机，消费者定义消息队列名（可以理解为生产者是食堂，食堂负责发放食物，吃饭的人相当于消费者，手里的饭盒相当消费者创建的队列，谁要吃饭谁创建自己的饭盒去吃。所以一般队列是在消费者端定义比较合理），当生产者启动后，消费者如果宕机或者未启动就会导致消息丢失，因为生产者先把消息发送给交换机，交换机没有存储功能，又由于没有消费者创建的queue，找不到绑定到exchange的queue，就会导致消息丢失。

解决方法：

一般在实际开发中要现在主函数项目启动时就把消费者启动起来等待生产者发送消息，也可以通过面板手动创建相关queue以防消息丢失（用面板创建的好处是将消费者和q解耦，q在面板创建好，如果此时消费者创建失败，q还是可以持久化消息，等待消费者重启后再次发送）

创建持久化队列(autoDelete = “false”表示持久化，相当于存盘，autoDelete = “true”表示非持久化，直接放内存，如果rabbitmq报错就会出现消息丢失)

这里的AD就代表当前的队列时非持久化的，一旦队列rabbitmq出问题，队列就会被删除

D代表持久队列

当关闭队列后，生产者再发消息就会持久化到queue里，而不会丢失，当rabbit宕机重启后，这里的消息数据还是在queue里的，因为开启了持久化存盘，只要你的生产者和消费者启动，会再次消费这些积留的数据。当堆积的消息过多时，一定要评估一下压力，直接启动消费者来直接消费可能扛不住的会把消息冲垮，造成消息丢失,这个qos,处理并发消息堆积的时候，这里可以使用basicQos里的false代表不批量消费，一个一个接收类似于限流。
